Social Distribution Federated social networking platform

A Django social network made up of independent nodes that communicate through authenticated REST APIs and per-author inboxes. The portfolio deployment runs two live nodes with separate PostgreSQL databases so cross-node follows, posts, comments, likes, and visibility rules can be demonstrated directly.

01 / OVERVIEW

Social Distribution is a federated social-networking platform originally developed as a CMPUT 404 team project at the University of Alberta. Each deployment owns its local authors and data, while trusted remote nodes exchange social activity through a shared API contract.

The portfolio version runs two independently deployed Heroku applications with separate PostgreSQL databases, seeded demo data, and automated resets so the federation flow can be explored without affecting a permanent user dataset.

02 / FEATURES

  • Local and remote author profiles
  • Cross-node follows, friendships, and follow requests
  • Public, unlisted, friends-only, and deleted posts
  • Comments and likes across trusted nodes
  • Inbox-based delivery for federated activity
  • HTTP Basic authentication between nodes
  • Fully qualified IDs for authors and content
  • Markdown, image posts, and optional GitHub activity import

03 / ARCHITECTURE

Node 1 and Node 2 each run Django + Django REST Framework on Heroku with their own PostgreSQL database. A node remains the source of truth for its local authors and content. Remote objects are identified with fully qualified URLs, and trusted nodes communicate through authenticated REST requests and per-author inbox endpoints.

05 / CHALLENGES

The main challenge was keeping ownership, identity, authentication, and visibility rules consistent while data crossed node boundaries. A local object could be viewed or acted on by a remote author, so API behavior had to stay predictable without treating cached remote data as locally owned data.

The project also required careful compatibility work around inbox payloads, fully qualified URLs, remote profiles, and failure cases so that one node could communicate with another without assuming both sides shared a database or application state.
